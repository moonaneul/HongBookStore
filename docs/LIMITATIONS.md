# HongBookStore Limitations & Evidence Boundaries

이 문서는 HongBookStore를 포트폴리오에서 과장 없이 설명하기 위한 기준입니다.

---

## 1. Team Result vs Personal Contribution

최종 Repository에는 팀 전체 기능이 함께 들어 있습니다.

따라서 Repository에 코드가 존재한다는 이유만으로 문하늘이 해당 기능을 직접 구현했다고 판단하지 않습니다.

### 개인 기여로 사용
- Requirement List
- Use Case
- 기능 / 정책 구체화
- 화면 구조
- Figma 설계
- Frontend 연결

### 팀 결과로만 사용
- Spring Backend 전체
- DB
- Redis
- WebSocket
- OAuth / Security
- Cloud / Deployment
- 외부 API 전체

---

## 2. Evidence Levels

### A. Repository에서 직접 확인되는 사실

- 최종 서비스에 React / Vite Frontend와 Spring Backend가 존재
- 초기 저장소에 Requirement List 파일 존재
- 단계별 기능 설명 파일 존재
- Use Case Diagram 파일 존재
- 의사결정 정리 파일 존재
- 주차별 요구사항 명세서 존재

### B. 사용자 확인 사실

- 4인 팀
- Requirement List / Use Case 대부분 직접 작성
- Figma 화면 설계 수행
- DB / Backend 담당 아님
- 기획 내용을 Frontend 구현까지 연결

### C. 현재 근거 부족으로 사용하지 않는 주장

- PM / 팀 리더 역할
- DB 설계
- Backend 아키텍처 설계
- 전체 Frontend 단독 개발
- 대규모 트래픽 처리
- 동시성 문제 해결
- 성능 개선 수치
- 사용자 수 / 전환율 / 시간 단축 수치

---

## 3. Figma Evidence

Figma 작업은 본인 확인 사실이지만 현재 Repository에 원본 링크나 export가 없습니다.

따라서 포트폴리오에서는 Figma를 사용했다고 쓸 수 있지만,

- 특정 화면 전체를 단독 설계
- 디자인 시스템 전체 구축

처럼 더 강한 범위를 주장하려면 원본 근거가 필요합니다.

---

## 4. Award

수상 여부는 별도 증거가 확인되기 전까지 이 Repository의 핵심 성과로 사용하지 않습니다.

공식 수상 증빙이 확보되면 연도 / 상명 / 주최기관을 정확히 확인한 뒤 추가합니다.

---

## 5. Safe Positioning

HongBookStore는 Backend 개발력을 보여주는 프로젝트로 과장하기보다,

> **요구사항을 구조화하고, 사용자 흐름과 화면으로 구체화한 뒤 구현까지 연결한 경험**

으로 사용하는 것이 현재 증거와 가장 잘 맞습니다.
